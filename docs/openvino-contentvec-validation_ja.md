# ContentVec 固定 shape / LATENCY 再検証（2026-09-15）

以下は採用前の比較記録。後続のユーザー承認に基づく製品実装と組み合わせ検証は
[モデル別構成の実装記録](openvino-model-routing_ja.md)を参照。

## 判断

- **ContentVec 固定は採用候補として継続する価値がある。** ContentVec 段階の平均は
  36.57 → 28.78 ms（約21%短縮）。ただし最終音声は一部条件で既存の最大絶対差閾値を
  超える。通常設定への一律採用は保留する。
- **LATENCY を平均だけで棄却しない。** 今回は平均がほぼ同じでも集計 p95 が
  535.85 → 511.69 ms、500 ms超過が44 → 36回に減った。一方 p99 は改善せず、
  巡回ごとの p95 改善は2/4回。候補としての価値は残るが、既定採用の根拠は不十分。
- **固定 ContentVec + LATENCY は今回採用しない。** 固定単独と比べ、4巡すべてで
  p95/p99 が悪化。両方を加えれば改善するとは言えない。

本番の通常コード・実行ファイル・設定は変更していない。実験は `target/contentvec-validation/`
内の独立したソースコピーと CLI で実施した。RVC は動的 shape、RMVPE は既存の
ORT CPU 回避策を維持。コミット・プッシュ・上流への投稿は行っていない。

## 条件と手順

- Intel Iris Xe / Core i7-1195G7、Windows 11、ドライバー32.0.101.7088。
- Windows ML OpenVINO EP 1.8.84.0、native OpenVINO 2026.2.1。
  GPU の `INFERENCE_PRECISION_HINT=f32` / `EXECUTION_MODE_HINT=ACCURACY` を全条件で維持。
- 同じ60秒人工信号、同じ RVC / ContentVec / RMVPE モデル、500 msチャンク。
  クロスフェード85 ms、SOLA探索12 ms、末尾破棄10 ms、追加文脈100 ms。
- 4条件を各4回、毎回別プロセスで実行。初期3チャンクと排出チャンクを除き117チャンク/回。
  起動・プリロール・WAV保存時間は定常処理から除外。各条件468チャンク。
- 順序を事前固定し、各条件が各実行位置に一度ずつ来るようにした。
  `B=基準 / L=LATENCY / F=固定ContentVec / FL=固定+LATENCY`。
  順序は `B,L,FL,F` → `L,F,B,FL` → `F,FL,L,B` → `FL,B,F,L`。
- RMVPE タスクのビルド・推論を停止してから性能測定を開始し、終了を連絡して再開した。
  測定中はこちらも重い解析やビルドを行っていない。既存キャッシュは維持。
  温度・電力状態・外部アプリは完全には統制していない。
- p95/p99 は nearest-rank。集計値は全468チャンクから再計算したもので、
  各回のパーセンタイルの平均ではない。チャンクは独立した468回の実験とは扱わない。
  期限超過はオフライン処理時間が500 msを超えた回数で、音声デバイスの実測アンダーランではない。

## 性能

### 全チャンク集計

| 条件 | 平均 ms | p95 ms | p99 ms | 最大 ms | 500 ms超過 / 468 | ContentVec平均 ms |
|---|---:|---:|---:|---:|---:|---:|
| 基準 | 476.38 | 535.85 | 633.42 | 1231.46 | 44 | 36.57 |
| LATENCY | 476.76 | 511.69 | 640.37 | 1980.81 | 36 | 36.30 |
| 固定ContentVec | 473.89 | 500.79 | 557.51 | 1936.27 | 25 | 28.78 |
| 固定ContentVec + LATENCY | 476.08 | 514.68 | 572.43 | 2095.95 | 41 | 28.33 |

固定単独の ContentVec p95 は38.59 → 30.56 ms、p99 は73.89 → 31.82 ms。
ContentVec平均の短縮は全4巡で確認した。一方、変換全体の平均短縮は約2.49 msにとどまる。
全体の p95/p99 が基準より改善した巡回は、固定単独でも2/4回だった。
最初の基準が特に遅いため、集計値だけで全体の改善を保証しない。

LATENCY 単独は基準比で p95改善2/4、p99改善3/4、超過回数改善2/4。

以前の単発測定で見えた尾側改善を認めたうえで、今回の反復では一貫性を確認できなかった。

1～2秒の突発的な遅れの多くは **RVC 段階のホスト計測時間** が占める。
例えば固定+LATENCY第3巡の最大2095.95 ms中、RVCは2025.56 ms、ContentVecは29.27 ms。
第4巡の基準最大1231.46 ms中もRVCが1162.58 ms。各条件で発生しており、
このログだけでGPUカーネル・ドライバー・OS待機のどれが原因かは断定しない。

起動面では基準のロード約4.6～5.2秒＋プリロール約4.0～4.8秒に対し、固定単独は
ロード約10.3～11.7秒＋プリロール約0.51～0.58秒。実験の固定ロード経路には
モデル調査と段階ウォームアップが含まれる。プリロールだけの短縮を起動全体の高速化とは呼ばない。

## ContentVec 単体精度

EPパッケージのnative DLLを絶対パスでプリロードし、OpenVINO CPU FP32を参照に、
GPU動的/固定を直接比較した。これはORT経由の演算配置の証明ではない。
入力長3840 / 11520 / 35520、無音・調波・シード固定雑音・周波数スイープの12条件。

通常の768次元出力 `unit12` について:

| 比較 | 最大絶対差の最大 | 相対RMS差の最大 |
|---|---:|---:|
| GPU固定 vs OpenVINO CPU | 2.81e-5 | 1.45e-5 |
| GPU固定 vs GPU動的 | 3.71e-5 | 7.92e-6 |

全12条件で `atol=1e-4, rtol=1e-4` を満たし、有限値だった。256次元出力も同許容値内。
モデルには拡大された別出力 `unit12s` もあり、その絶対差まで同じ尺度で合格とはしていない。
入力の種類と長さは限定されており、これだけで全入力の正しさを保証しない。

## 音声差と入力長

参照は同じ共有変換パイプラインの動的GPU条件。WAV保存前のfloat32も保存し、
そのままfloat WAVとして既存 `tools/audio_compare` で比較した。
閾値は **最大絶対差1e-4、相対RMS差1e-3、LSD 0.5 dB** のまま。

| 入力 / チャンク / 追加文脈 | ContentVec入力長 | float最大絶対差 | float相対RMS差 | float LSD dB | float判定 | PCM16 LSD dB |
|---|---:|---:|---:|---:|---|---:|
| 2秒調波16 kHz / 20 ms / 100 ms | 3840 | 4.33e-5 | 1.13e-5 | 0.0126 | 合格 | 0.5166 |
| 同 / 30 ms / 100 ms | 3840 | 8.08e-5 | 1.97e-5 | 0.0123 | 合格 | 0.5318 |
| 同 / 500 ms / 100 ms | 11520 | 4.19e-6 | 1.17e-5 | 0.0177 | 合格 | 0.8493 |
| 同 / 2000 ms / 100 ms | 35520 | 2.38e-5 | 1.44e-5 | 0.0108 | 合格 | 0.6543 |
| 3.173秒変動信号44.1 kHz / 30 ms / 125 ms | 4480 | 1.95e-4 | 7.32e-5 | 0.00546 | 最大差で不合格 | 0.3406 |
| 同48 kHz / 30 ms / 125 ms | 4480 | 1.47e-4 | 4.45e-5 | 0.00312 | 最大差で不合格 | 0.2586 |
| 60秒人工信号16 kHz / 500 ms / 100 ms | 11520 | 2.08e-4 | 3.76e-5 | 0.0166 | 最大差で不合格 | 0.7757 |

PCM16の総合判定は全7条件で不合格。短い16 kHz信号はLSD、44.1/48 kHz信号は最大差、
60秒信号は両方が閾値を超える。最大差の超過まで量子化だけが原因とはしていない。

以前の2秒/500 msの差は、32000サンプル中1076個（3.36%）がPCM16の±1段階。
差のRMSは約−105 dBFS。量子化前のLSDは0.0177 dBに収まり、保存後は0.8493 dB。
補助的な倍精度FFT分析では、弱い周波数成分がdB差の大半を占める。
小さな推論差がPCM16の丸め境界をまたぐことが、以前のLSD不合格に大きく寄与している。
補助分析は既存の閾値を置き換えるものではない。

60秒信号では、LATENCY単独の出力は各巡の基準とfloat/PCM16とも完全一致。
固定+LATENCYの出力は固定単独と同じ比較値となり、LATENCYによる精度改善は見られない。
量子化前でも最大差が残るため、「固定ContentVecは完全に正しい」とは判定しない。
60秒信号の量子化前の差RMSは約−102.3 dBFSで、PCM16差が1e-4を超えるのは
191/960000サンプル（約0.020%）、最大±7段階だった。44.1/48 kHz信号での同超過は
81/139929、23/152304サンプル。差は少数のサンプルに偏るが、これを根拠に閾値違反を合格へ変えない。
量子化前の小差を生む演算までの特定は今回していない。
全般のRMS差は小さいが、実音声の試聴は未実施。人工信号での低いRMS/LSDだけで聴感品質を保証しない。

全ケースで参照と出力サンプル数が一致し、変換は正常終了した。30 msの端数最終チャンク、
44.1/48 kHzのレート変換、追加文脈の変更を含めた。
ContentVec入力は共有 `tensor_rt_model_input_samples_16k` で、音声チャンクに出力余裕
（85+12+10=107 ms）と追加文脈を加え、320サンプル単位へ切り上げている。
20/30 msが同じ3840に入るのはこの切り上げの結果で、進行幅まで固定値へ変えてはいない。
稼働中にサンプルレートやチャンク長を変える場合は既存の `validate_process_timing` に従い
パイプラインを再ロードする。未指定の他設定・他モデルまで網羅した検証ではない。

## 残る採用条件と保存物

固定ContentVecを進める場合は、最大差超過の位置・頻度を実音声でも評価し、
聴感と既存の品質基準を満たす範囲を決める必要がある。今回の結果に合わせて閾値を緩めてはいない。
LATENCYはp95改善候補として残すが、固定単独と組み合わせる既定値にはしない。

実験ソース・差分・バイナリハッシュ、実行引数・モデル/EPハッシュ、各チャンク時間、
PCM16/float出力、比較JSON、集計JSON、再実行スクリプトは `target/contentvec-validation/` に保存。
`protocol.md`、`run-matrix.ps1`、`summary.json`、`accuracy/`、`performance/`、`embedding/` を参照。
通常ソースと実験コピーの差分は `sessions.diff` / `pipeline.diff` / `engine.diff`。
初回のbootstrap DLL不足は失敗ログを保存し、既存DLLを実験実行ファイルの隣にコピーして解決した。
システムのランタイムやドライバーは変更していない。

検証: 独立コピーのWindows ML CLI releaseビルド成功、native単体12条件、
共有パイプライン精度12実行、性能16実行、PCM16/floatの既存比較ツールによる判定。
既存の未コミット作業・上流バグ報告草案は保持している。
